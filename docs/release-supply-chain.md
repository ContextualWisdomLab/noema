# Release Supply-Chain Evidence

## Purpose

Noema's `release-evidence` workflow produces a buyer-verifiable evidence bundle for an exact semantic-version tag. The bundle proves that the published **source archive** and its CycloneDX software bill of materials were generated by the repository's trusted GitHub Actions workflow from the exact tagged commit on a GitHub-hosted runner.

This evidence **does not prove deployment** to Cloudflare, production configuration, runtime health, customer use, revenue, or 30-day KPI performance. Those claims remain covered by the deployment smoke evidence, production provenance, saleable-readiness audit, and acquisition-readiness evidence.

## Release boundary

The workflow accepts only an existing `vMAJOR.MINOR.PATCH` tag whose value matches `package.json` and whose checked-out commit is the tag target. A manual run must be dispatched with `--ref` set to that same tag; running default-branch workflow code while naming a different tag is rejected.

The workflow:

1. Checks out the exact tag without persisting Git credentials.
2. Runs `npm ci` and `npm run release:verify`.
3. Creates a deterministic Git source archive named `noema-<commit-sha>.tar.gz`.
4. Creates a lockfile-derived CycloneDX 1.5 application SBOM named `noema.cdx.json`.
5. Validates repository, tag, commit, package version, SBOM root component, and bounded regular-file inputs.
6. Writes `release-evidence.json` and `SHA256SUMS`.
7. Generates separate GitHub/Sigstore provenance and CycloneDX SBOM attestations for the source archive.
8. Verifies both attestations against the exact signer workflow, signer/source digest, tag ref, GitHub Actions OIDC issuer, and GitHub-hosted-runner policy before publishing the artifact.

No deployment credentials, GitHub App private key, LLM key, or Cloudflare secret are available to this workflow.

## Evidence bundle

The artifact `noema-release-evidence-v<version>` is retained for 90 days and contains:

| File | Meaning |
|---|---|
| `noema-<commit-sha>.tar.gz` | Git-generated source archive of the exact release commit. |
| `noema.cdx.json` | CycloneDX 1.5 SBOM generated from `package-lock.json` as an application BOM. |
| `release-evidence.json` | Bounded manifest tying repository, commit SHA, tag ref, version, byte sizes, component counts, and SHA-256 digests together. |
| `SHA256SUMS` | Offline integrity list for the source archive, SBOM, and evidence manifest. |
| `attestations/provenance.sigstore.json` | In-toto/SLSA-style build provenance bundle for the source archive. |
| `attestations/cyclonedx-sbom.sigstore.json` | In-toto CycloneDX SBOM attestation bundle for the source archive. |

An artifact copied outside GitHub remains useful only when its checksums and attestation bundles are preserved together.

## Producing evidence

### Tag-triggered run

```bash
git tag -s v0.1.0 <release-commit-sha>
git push origin v0.1.0
```

The tag must equal `v` plus the version in `package.json`.

### Manual rerun for an existing tag

```bash
gh workflow run release-evidence.yml \
  --repo ContextualWisdomLab/noema \
  --ref v0.1.0 \
  -f tag=v0.1.0
```

The explicit `--ref` is mandatory. It binds the workflow source ref and attestation source ref to the release tag rather than `main`.

## Offline checksum verification

Extract the artifact into one directory, then run:

```bash
cd noema-release-evidence-v0.1.0
sha256sum --check SHA256SUMS
```

Every line must report `OK`. A checksum match proves byte integrity relative to `SHA256SUMS`; it does not authenticate who generated that checksum file. Authenticate provenance with the attestation steps below.

## Online attestation verification

Set the release identity from the bundle:

```bash
export NOEMA_RELEASE_SHA=<40-character-release-commit-sha>
export NOEMA_RELEASE_TAG=v0.1.0
export NOEMA_ARCHIVE="noema-${NOEMA_RELEASE_SHA}.tar.gz"
```

Verify source provenance:

```bash
gh attestation verify "$NOEMA_ARCHIVE" \
  --bundle attestations/provenance.sigstore.json \
  --repo ContextualWisdomLab/noema \
  --signer-workflow ContextualWisdomLab/noema/.github/workflows/release-evidence.yml \
  --signer-digest "$NOEMA_RELEASE_SHA" \
  --source-digest "$NOEMA_RELEASE_SHA" \
  --source-ref "refs/tags/${NOEMA_RELEASE_TAG}" \
  --cert-oidc-issuer https://token.actions.githubusercontent.com \
  --deny-self-hosted-runners
```

Verify that the source archive is bound to the CycloneDX predicate:

```bash
gh attestation verify "$NOEMA_ARCHIVE" \
  --bundle attestations/cyclonedx-sbom.sigstore.json \
  --repo ContextualWisdomLab/noema \
  --signer-workflow ContextualWisdomLab/noema/.github/workflows/release-evidence.yml \
  --signer-digest "$NOEMA_RELEASE_SHA" \
  --source-digest "$NOEMA_RELEASE_SHA" \
  --source-ref "refs/tags/${NOEMA_RELEASE_TAG}" \
  --cert-oidc-issuer https://token.actions.githubusercontent.com \
  --predicate-type https://cyclonedx.org/bom \
  --deny-self-hosted-runners
```

Do not remove the signer, digest, source-ref, issuer, or runner restrictions for buyer due diligence. A generic identity match is weaker than the release policy.

## Downloading independent attestation material

When GitHub access is available, an auditor can independently retrieve stored attestations for the source archive digest:

```bash
gh attestation download "$NOEMA_ARCHIVE" \
  --repo ContextualWisdomLab/noema \
  --digest-alg sha256 \
  --output attestations-from-github.jsonl
```

Compare the downloaded statements with the bundles shipped in the release artifact and re-run `gh attestation verify` under the strict policy above.

## Air-gapped verification

Before entering the disconnected environment, export GitHub's Sigstore trusted root:

```bash
gh attestation trusted-root > github-trusted-root.jsonl
```

Copy the source archive, `SHA256SUMS`, both attestation bundles, and `github-trusted-root.jsonl` into the isolated environment. Verify integrity first, then verify each bundle with the custom root:

```bash
sha256sum --check SHA256SUMS

gh attestation verify "$NOEMA_ARCHIVE" \
  --bundle attestations/provenance.sigstore.json \
  --custom-trusted-root github-trusted-root.jsonl \
  --repo ContextualWisdomLab/noema \
  --signer-workflow ContextualWisdomLab/noema/.github/workflows/release-evidence.yml \
  --signer-digest "$NOEMA_RELEASE_SHA" \
  --source-digest "$NOEMA_RELEASE_SHA" \
  --source-ref "refs/tags/${NOEMA_RELEASE_TAG}" \
  --cert-oidc-issuer https://token.actions.githubusercontent.com \
  --deny-self-hosted-runners

gh attestation verify "$NOEMA_ARCHIVE" \
  --bundle attestations/cyclonedx-sbom.sigstore.json \
  --custom-trusted-root github-trusted-root.jsonl \
  --repo ContextualWisdomLab/noema \
  --signer-workflow ContextualWisdomLab/noema/.github/workflows/release-evidence.yml \
  --signer-digest "$NOEMA_RELEASE_SHA" \
  --source-digest "$NOEMA_RELEASE_SHA" \
  --source-ref "refs/tags/${NOEMA_RELEASE_TAG}" \
  --cert-oidc-issuer https://token.actions.githubusercontent.com \
  --predicate-type https://cyclonedx.org/bom \
  --deny-self-hosted-runners
```

The trusted-root export should be captured close to the verification date and retained in the buyer data room with its retrieval date and source.

## SBOM review

Basic structural inspection:

```bash
jq '{
  bomFormat,
  specVersion,
  serialNumber,
  root: .metadata.component,
  component_count: (.components | length),
  dependency_count: (.dependencies | length)
}' noema.cdx.json
```

The root must be the `noema` application at the release version. Dependency entries are generated from the committed lockfile, so the SBOM describes the source dependency resolution used by the release workflow. It is not an inventory of Cloudflare platform components or production infrastructure.

## Failure policy

Evidence publication fails closed when any of these conditions is true:

- the tag is not strict semantic versioning;
- the workflow is not running at the named tag ref;
- the package version differs from the tag;
- the checked-out commit differs from the tag target;
- release tests or security checks fail;
- source or SBOM input is missing, empty, oversized, a symlink, or incorrectly named;
- the SBOM is not CycloneDX 1.5, lacks an application root, or identifies another product/version;
- checksum verification fails;
- either provenance or SBOM attestation fails the exact-workflow policy.

No partially generated bundle should be treated as release evidence.

## Due-diligence interpretation

A passing bundle supports these claims:

- the archive bytes match the recorded SHA-256 digest;
- the archive came from an exact Noema tag/commit processed by the pinned release workflow;
- the workflow ran the repository's release gate before attestation;
- a CycloneDX SBOM was associated with that exact source archive;
- the workflow used GitHub Actions OIDC and a GitHub-hosted runner under the verification policy.

It does not establish production deployment, operating effectiveness over time, absence of all vulnerabilities, legal ownership of every dependency, customer acceptance, revenue, or transfer completion. Those require separate evidence in the buyer due-diligence index.
